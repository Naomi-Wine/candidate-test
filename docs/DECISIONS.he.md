# החלטה 001: להישאר בטכנולוגיה ובארכיטקטורה של הסטרטר

**סטטוס:** הוכרע

## הסוגיה

מסמך הדרישות מציין במפורש: *"ניתן להשתמש ב-Backend הקיים או לממש בטכנולוגיה אחרת. אם בחרת טכנולוגיה שונה, ציין ב-README מדוע."*

עלתה השאלה האם ההיתר הזה הוא רמז שכדאי לשכתב, ובאיזו מידה נכון לשנות את מבנה הסטרטר.

## מה קיים בסטרטר

.NET 8 בארכיטקטורת Clean/Onion, מחולק לארבעה פרויקטים:

| פרויקט | תוכן |
|---|---|
| `Requests.Domain` | `Request` Entity, `RequestStatus`, `RequestType` |
| `Requests.Application` | `IRequestService`, `RequestService`, `IRequestRepository`, `RequestDto` |
| `Requests.Infrastructure` | EF Core (InMemory), `RequestRepository`, `DbSeeder` |
| `Requests.Api` | `RequestsController`, `Program.cs` |

כיוון התלויות תקין: `Domain` לא מפנה לאף פרויקט, `Infrastructure` מפנה ל-`Application` (Dependency Inversion).

## החלופות שנשקלו

### א. שכתוב לטכנולוגיה אחרת (Node / Java)

- **בעד:** מותר במפורש.
- **נגד:** המשרה היא .NET + Angular. השקעת זמן משמעותית בלי תמורה לדרישות עצמן.

### ב. שכתוב ל-Vertical Slice Architecture

ארגון לפי פיצ'ר במקום לפי שכבה.

- **בעד:** גישה מודרנית, פחות קפיצות בין פרויקטים.
- **נגד:** דורש פירוק מלא של הסטרטר. שעות עבודה שלא תורמות לאף דרישה במסמך.

### ג. הוספת CQRS + MediatR

- **בעד:** דפוס נפוץ בפרויקטי .NET ארגוניים.
- **נגד:** יש כאן **פיצ'ר קריאה אחד**. Command/Query separation בלי Commands הוא תקורה ריקה.

### ד. להישאר במבנה ולתקן את מה ששבור בתוכו ✅

## ההחלטה

**להישאר ב-.NET 8 ובארכיטקטורת ארבע השכבות, ולהתמקד בתיקון שכבת הנתונים.**

## הנימוקים

1. **המבנה תקין.** כיוון התלויות נכון, ההפרדה ברורה, הלוגיקה ניתנת לבדיקה ללא DB. אין כאן מה לתקן ברמת הארכיטקטורה.

2. **הבעיה האמיתית נמצאת במקום אחר.** `RequestRepository.GetAllAsync` מבצע `ToListAsync()` על כל הטבלה. בשילוב עם הדרישה "יש להניח מיליוני רשומות" — זה הליקוי שהמשימה בודקת.

3. **המסמך מנחה במפורש לפשטות:** *"אנו מעדיפים פתרון פשוט, ברור ומנומק על פני מורכב שלא נדרש."*

4. **שיקול ראיון.** במסמך נכתב שבראיון ההמשך ייתכן שיתבקש הסבר או שינוי של חלק מהפתרון. מבנה מוכר לעומק עדיף על מבנה מרשים שנכתב במהירות.

## מה כן שונה בתוך המבנה

- שכבת הנתונים: מעבר מ-`GetAllAsync` לשליפה מסוננת ב-`IQueryable`
- הוספת קובץ `.sln`
- הגדרת CORS (חסרה, נדרשת לחיבור Angular)
- הפרדת רישום ה-DI: `AddApplication()` בנפרד מ-`AddInfrastructure()`
- חילוץ קריאת ה-headers מהקונטרולר ל-`ICurrentUser`
- הוספת `client/` לפרויקט ה-Angular

## מתי ההחלטה הייתה משתנה

- אם הסטרטר היה מכיל הפרות ארכיטקטורה אמיתיות (למשל `DbContext` בקונטרולר)
- אם היו נדרשים גם Commands ולא רק Query — אז CQRS היה מקבל הצדקה
- אם הצוות היה עובד ב-Vertical Slice כסטנדרט

# החלטה 002: `GET` עם Query Parameters (ולא `POST /search`)

**סטטוס:** הוכרע

## הסוגיה

הפילטר כולל מספר שדות: `requestNumber`, רשימת סטטוסים, טווח תאריכים, סוג בקשה, פרמטרי מיון ו-paging.

השאלה: להעביר אותם כ-query parameters ב-`GET`, או כאובייקט JSON ב-body של `POST`?

## החלופות שנשקלו

### א. `POST /api/requests/search` עם אובייקט ב-body

```http
POST /api/requests/search
Content-Type: application/json

{
  "requestNumber": "REQ-001",
  "statuses": ["New", "InProgress"],
  "fromDate": "2025-01-01",
  "toDate": "2025-06-30",
  "page": 1,
  "pageSize": 25
}
```

זהו דפוס מוכר בשם **Search Endpoint** או **POST-for-query**.

**יתרונות:**

| יתרון | הסבר |
|---|---|
| מבנה מקונן | מאפשר פילטרים דינמיים עם אופרטורים (`in`, `between`) — דבר שלא ניתן לבטא בנוחות ב-query string |
| אין הגבלת אורך | URL מוגבל למעשה ל-2,000–8,000 תווים. רשימת מזהים ארוכה תישבר |
| Typing חזק | אובייקט אחד מוגדר היטב משני הצדדים, בלי בניית `HttpParams` ידנית |
| אין דליפה ללוגים | Query strings נשמרים ב-access logs, ב-proxy וב-browser history. Body לא |

**חסרונות:**

| חיסרון | הסבר |
|---|---|
| שבירת סמנטיקת HTTP | `GET` הוא safe ו-idempotent. `POST` מסמן לתשתית "פעולה שמשנה מצב" — וחיפוש אינו כזה |
| אובדן caching | Browser cache, CDN, reverse proxy ו-`ETag`/`304` מפסיקים לעבוד |
| אין קישור לשיתוף | לא ניתן לשמור את החיפוש כמועדף, לשלוח אותו, או לשחזר אותו לאחר רענון |
| סטייה מ-REST | דורש נתיב `/search` נפרד, שאינו משאב |
| Debugging מסורבל | לא ניתן לשחזר בדפדפן או ב-`curl` בלי בניית body |

### ב. `GET /api/requests` עם query parameters ✅

```http
GET /api/requests?requestNumber=REQ-001&status=New&status=InProgress&fromDate=2025-01-01&page=1&pageSize=25
```

## ההחלטה

**`GET /api/requests` עם query parameters.**

## הנימוקים

1. **הפילטר שטוח לחלוטין.** חמישה שדות פשוטים, שאחד מהם מרובה. היתרון המרכזי של `POST` — מבנה מקונן — אינו רלוונטי כאן.

2. **קישור ניתן לשיתוף חשוב לטבלת סינון.** משתמש שמסנן, מרענן ומאבד את המצב — זו חוויה גרועה. ב-`GET` זה מתקבל ללא עלות.

3. **Caching רלוונטי.** טבלה עם paging מייצרת קריאות חוזרות על אותם פרמטרים.

4. **אין מידע רגיש בפילטר.** `requestNumber` הוא מזהה עסקי, השאר enums ותאריכים. זהות המשתמש עוברת ב-header ולא ב-URL, כך שהחלק הרגיש כבר אינו בכתובת.

5. **פחות קוד.** `[FromQuery]` הוא binding מובנה. `POST` דורש endpoint נפרד וטיפוס בקשה נוסף.

## מתי ההחלטה הייתה משתנה

הייתי מוסיפה `POST /api/requests/search` **לצד** ה-`GET` — לא במקומו — אם:

- הפילטר היה מתפתח לאופרטורים דינמיים לכל שדה
- היו נדרשות רשימות ארוכות של מזהים (מאות ומעלה)
- הפילטר היה מכיל מידע אישי מזהה שאסור שיגיע ללוגים

# החלטה 003: העברת Status מרובה — חזרה על הפרמטר

**סטטוס:** הוכרע

## הסוגיה

הדרישה: סינון לפי סטטוס, **בערך יחיד או במספר ערכים**.

Query string הוא מבנה שטוח של `key=value` ואין בו מושג מובנה של מערך. קיימות מספר קונבנציות להעברת רשימה.

## החלופות שנשקלו

### א. חזרה על הפרמטר (Repeated / Multi-value) ✅

```
?status=New&status=InProgress
```

**Backend — binding מובנה, ללא קוד נוסף:**

```csharp
public sealed class RequestFilterQuery
{
    public List<RequestStatus>? Status { get; init; }
}

[HttpGet]
public async Task<IActionResult> Get(
    [FromQuery] RequestFilterQuery query, CancellationToken ct)
```

ה-model binder מזהה יעד מסוג אוסף, אוסף את כל המופעים וממיר כל אחד ל-enum.

**Frontend — נתמך מובנה:**

```typescript
let params = new HttpParams();
filter.statuses?.forEach(s => params = params.append('status', s));
//                                        ^^^^^^ append ולא set
```

> `HttpParams` הוא immutable. `append` מוסיף מופע נוסף, `set` היה דורס את הקודם. זו טעות נפוצה בגישה הזו.

### ב. CSV — ערכים מופרדים בפסיק

```
?status=New,InProgress
```

**יתרון:** ה-URL קצר וקריא יותר.

**חיסרון:** ASP.NET Core אינו מפצל את המחרוזת. הוא ינסה להמיר `"New,InProgress"` לערך enum בודד וייכשל. נדרש `IModelBinder` או `TypeConverter` מותאם — כ-30 שורות קוד תשתית, רישום, וטסטים משלו.

בעיה נוספת: הגישה נשברת אם ערך כלשהו מכיל פסיק. לא רלוונטי ל-enums, אך חולשה מובנית.

### ג. סוגריים מרובעים

```
?status[]=New&status[]=InProgress
```

קונבנציה מעולם PHP ו-Rails. אינה קונבנציה ב-.NET ודורשת קוד מותאם ללא תועלת נוספת.

## ההשוואה

| | חזרה על הפרמטר | CSV | סוגריים |
|---|---|---|---|
| Binding ב-.NET | ✅ מובנה | ❌ דורש binder | ❌ דורש binder |
| Angular `HttpParams` | ✅ מובנה | דורש `join(',')` | בנייה ידנית |
| תקן HTML / OpenAPI | ✅ ברירת מחדל | נתמך, לא ברירת מחדל | לא בתקן |
| Swagger UI | ✅ שדה מרובה | תיבת טקסט | לא נתמך |
| אורך ה-URL | בינוני | ✅ הקצר ביותר | בינוני |
| ערך המכיל פסיק | ✅ תקין | ❌ נשבר | ✅ תקין |

## ההחלטה

**חזרה על הפרמטר: `?status=New&status=InProgress`**

## הנימוקים

זו הצורה שבה **שני הצדדים תומכים מובנה**. אין שכבת תרגום, אין קוד תשתית לתחזוקה, ואין טסטים ל-parser עצמי.

ה-CSV אינו פשוט יותר — הוא **נראה** פשוט יותר ב-URL, ומשלם על כך בקוד. התועלת אסתטית בלבד.

## החלטות נלוות

### שם הפרמטר: `status` ביחיד

`?status=New&status=InProgress` קורא טבעי יותר מ-`?statuses=...`, שבו כל מופע נשמע כאילו הוא רשימה בפני עצמה. הקונבנציה המקובלת היא שם יחיד שחוזר.

### `null` ולא רשימה ריקה

```csharp
public List<RequestStatus>? Status { get; init; }
```

| ערך | משמעות |
|---|---|
| `null` | לא התבקש סינון → מחזירים הכל |
| רשימה ריקה | מקרה קצה מבלבל — מטופל כמו `null` |

```csharp
if (filter.Status is { Count: > 0 })
    query = query.Where(r => filter.Status.Contains(r.Status));
```

הביטוי `is { Count: > 0 }` מטפל ב-`null` ובריק בבת אחת.

### ערך לא חוקי → `400`, ולא התעלמות שקטה

`?status=Banana` יוסיף שגיאה ל-`ModelState`, ותכונת `[ApiController]` תחזיר `400 Bad Request` עם `ProblemDetails` אוטומטית.

זה עונה לדרישה "טיפול בקלט לא חוקי". **התעלמות שקטה מערך לא מוכר היא באג** — הלקוח יקבל תוצאות שלא ביקש ולא יידע על כך.

### תרגום ל-SQL

`Contains` על רשימה מתורגם ל-`IN`:

```sql
WHERE [r].[Status] IN (1, 2)
```

הפעלת logging של EF מאפשרת לוודא שהסינון אכן יורד ל-DB ואינו רץ בזיכרון.

## מתי ההחלטה הייתה משתנה

- אם היו נדרשים עשרות ערכים בפילטר בודד — אורך ה-URL היה הופך לשיקול
- אם הפרויקט היה מאמץ קונבנציית CSV כסטנדרט רוחבי — עקביות גוברת על נוחות מקומית

# החלטה 004: Paging

**סטטוס:** הוכרע

## הסוגיה

הדרישות מציינות *"יש להניח מיליוני רשומות"*. החזרת כל התוצאות אינה אפשרית, ולכן נדרש מנגנון שמחזיר חלון של תוצאות בכל בקשה.

ההחלטה מתפצלת לשלוש שאלות נפרדות:

1. באיזו **פרדיגמה** — Offset או Cursor?
2. באיזה **ניסוח פרמטרים** — `page`/`pageSize` או `skip`/`take`?
3. האם הקליינט **שומר buffer** גדול ממה שהוא מציג?

---

## 4א. הפרדיגמה: Offset מול Cursor

### Cursor / Keyset Pagination

במקום "דלג על N רשומות", מבקשים "החזר את מה שבא אחרי הרשומה הזו":

```sql
SELECT TOP 25 * FROM Requests
WHERE (CreatedAt, Id) < ('2025-06-01', 42)
ORDER BY CreatedAt DESC, Id DESC
```

| | Offset | Cursor / Keyset |
|---|---|---|
| ביצועים בעמוד 1 | מהיר | מהיר |
| ביצועים בעמוד 10,000 | ❌ איטי — המסד סורק וזורק את כל השורות שלפני החלון | ✅ מהיר, זהה לעמוד 1 |
| ניצול אינדקס | חלקי | ✅ מלא |
| עקביות בזמן שינויים | ❌ כפילויות ודילוגים כשנתונים משתנים בין קריאות | ✅ יציב |
| קפיצה לעמוד שרירותי | ✅ אפשרי | ❌ בלתי אפשרי |
| `totalCount` ו"עמוד 3 מתוך 12" | ✅ | ❌ לא קיים |
| מיון שהמשתמש בוחר | ✅ | ❌ כל שינוי מיון מבטל את ה-cursor |
| מורכבות מימוש | נמוכה | גבוהה יותר |

### ההחלטה: Offset

למרות שהוא נחות טכנית בעומק, ומודעים לכך:

1. **הדרישות מבקשות טבלה, לא feed.** משתמש בטבלה ניהולית מצפה לקפוץ לעמוד, לראות כמה עמודים קיימים, ולחזור אחורה. Cursor שולל את שלושתם.
2. **הדרישות מבקשות מיון שהמשתמש בוחר.** כל שינוי מיון מבטל cursor קיים — סתירה מובנית.
3. **`totalCount` נדרש מרומז** — בלעדיו אין "עמוד 3 מתוך 12" ואין השבתה נכונה של כפתור "הבא".

**מתי היה משתנה:** feed עם infinite scroll, מיון קבוע, וללא צורך בקפיצה לעמוד — Keyset היה הבחירה הנכונה.

---

## 4ב. ניסוח הפרמטרים

שתי האפשרויות **זהות מתמטית** — `skip = (page - 1) × pageSize`. זו בחירה של ממשק, לא של טכנולוגיה.

### `skip` + `take`

| יתרונות | חסרונות |
|---|---|
| מיפוי ישיר ל-LINQ, אפס המרה | לא מדבר בשפת ה-UI — הטבלה עדיין מחשבת `page` |
| אין שאלת בסיס-0/1 | פחות קריא: `?skip=1250` — באיזה עמוד אני? |
| גמיש — כל חלון, גם לא מיושר לעמוד | מזמין מצבים לא עקביים (`skip=7&take=25`) |
| נוח ל-infinite scroll | חושף פרט מימוש (מונחי LINQ/SQL) |

### `page` + `pageSize` ✅

| יתרונות | חסרונות |
|---|---|
| מדבר בשפת מה שה-UI מציג | שאלת בסיס 0/1 — מקור קבוע לבאגים |
| `totalPages = ceil(total / pageSize)` טריוויאלי | דורש המרה בשרת |
| רכיבי Pagination בנויים סביב `pageIndex`/`pageSize` | לא ניתן לבקש חלון שרירותי |
| URL קריא: `?page=3` | |

### ההחלטה: `page` + `pageSize`, בסיס 1

ה-API צריך לדבר בשפת התחום ולא בשפת המימוש. `skip`/`take` הם מונחי LINQ שחושפים כיצד הדבר ממומש; `page`/`pageSize` מתארים מה הלקוח רוצה. הפשטה זו גם מאפשרת מעבר עתידי ל-Keyset בלי לשבור את חוזה הלקוח.

```
GET /api/requests?page=1&pageSize=25
```

> **הערה למימוש:** `MatPaginator` של Angular Material משתמש ב-`pageIndex` שמתחיל מ-**0**, בעוד ה-API מתחיל מ-**1**. בעקבות החלטה 011 הרכיב אכן בשימוש, ולכן ההמרה נדרשת ומתבצעת בשני מקומות מוגדרים בלבד: בקריאת `page` מהכתובת אל הרכיב (`pageIndex = page - 1`), ובאירוע `(page)` היוצא ממנו אל הכתובת (`page = pageIndex + 1`). ריכוז ההמרה בשתי נקודות מוגדרות הוא מה שמונע מהפער להתפזר בקוד — זהו מקור הבאגים הידוע של הרכיב הזה.

## 4ג. גודל העמוד ו-Buffer בקליינט

### הסוגיה

עלתה שאלה: האם נכון להביא מהשרת יותר רשומות ממה שמוצג — למשל להציג 10 ולשלוף 20 — כדי לחסוך קריאות רשת?

### ניתוח העלות

עלות בקשת API בודדת מתחלקת כך:

| רכיב | זמן |
|---|---|
| Round trip ברשת | 1–20ms |
| שאילתה עם אינדקס | 1–5ms |
| סריאליזציה + העברה של עמוד | <2ms |

| | 10 רשומות | 20 רשומות |
|---|---|---|
| סה"כ | ~22ms | ~23ms |

**רוב העלות היא ה-round trip עצמו, לא הנפח.** הכפלת גודל העמוד כמעט אינה משנה את זמן התגובה, ולכן חיסכון של מחצית הבקשות חוסך אחדות בודדות של מילישניות.

### מחיר ה-Buffer

| מצב | מה נשבר |
|---|---|
| קפיצה לעמוד רחוק | ה-buffer אינו רלוונטי, נדרשת שליפה מחדש |
| שינוי מיון | ה-buffer ממוין לפי הסדר הישן — לא תקף |
| שינוי פילטר | ה-buffer אינו תקף כלל |
| נתונים שהשתנו בשרת | ה-buffer מציג מצב מיושן |

כל אחד מהמצבים דורש קוד סנכרון נוסף ומהווה מקום פוטנציאלי לבאג שקשה לשחזר.

### השיקול המכריע: נכונות, לא ביצועים

מיון וסינון על תת-קבוצה שנשמרה בזיכרון **מחזירים תוצאה שגויה**. אם 20 רשומות נשמרו מתוך 500, מיון בקליינט ימיין 20 מתוך 500 — והרשומה הרלוונטית ביותר ככל הנראה אינה ביניהן.

מכיוון שהדרישות כוללות סינון ומיון, שניהם **חייבים** לרוץ על מלוא הנתונים, כלומר במסד.

### ההחלטה

**שליפה של בדיוק כמות הרשומות המוצגת. ללא buffer בקליינט.**

| פרמטר | ערך |
|---|---|
| `pageSize` ברירת מחדל | 25 |
| אפשרויות למשתמש | 10 / 25 / 50 / 100 |
| תקרת שרת | 100 |
| חריגה מהתקרה | `400 Bad Request` |
| `page` ברירת מחדל | 1 |

הקליינט מחזיק שני מספרים בלבד — `page` ו-`pageSize` — ולא מטמון נתונים. כל שינוי (עמוד, סינון או מיון) הוא בקשה אחת שחוזרת מסוננת וממוינת מהמסד.

> **הערה על 500 הרשומות ב-InMemory:** אלו נתוני seed לצורך הפיתוח בלבד. ההחלטות התקבלו לפי הדרישה המוצהרת — מיליוני רשומות — ולא לפי היקף ה-seed.

**מתי ההחלטה הייתה משתנה:** אילו היה מדובר ב-infinite scroll ללא מיון משתנה, או ברשת בעלת latency גבוה במיוחד, הייתה מקום ל-prefetch של העמוד הבא. זו אופטימיזציה שהייתי מוסיפה לאחר מדידה, לא בתכנון הראשוני.

## פרטי מימוש שנקבעו

### מיון יציב — חובה

```csharp
query = query
    .OrderByDescending(r => r.CreatedAt)
    .ThenBy(r => r.Id);          // tie-breaker
```

ללא מיון משני על שדה ייחודי, רשומות בעלות אותו `CreatedAt` עלולות לקבל סדר שונה בין שאילתות — ואותה רשומה תופיע בשני עמודים או תיעלם.

### שתי שאילתות, שתיהן על `IQueryable` מסונן

```csharp
var totalCount = await query.CountAsync(ct);

var items = await query
    .OrderByDescending(r => r.CreatedAt)
    .ThenBy(r => r.Id)
    .Skip((page - 1) * pageSize)
    .Take(pageSize)
    .Select(r => new RequestDto(r.Id, r.RequestNumber, r.Status, r.CreatedAt))
    .ToListAsync(ct);
```

- `CountAsync` מופעל לפני `Skip`/`Take`, על אותם תנאי סינון
- ה-`Select` מופיע לפני `ToListAsync`, כך שה-projection יורדת ל-SQL ורק העמודות הנדרשות נשלפות
- אין `ToListAsync` באמצע השרשרת — הכל נשאר `IQueryable` עד הסוף

### תקרת `pageSize` — שיקול אבטחה

ללא תקרה, `?pageSize=99999999` מבטל את ה-paging ומהווה וקטור ל-DoS. התקרה נאכפת בשרת ואינה ניתנת לעקיפה מהלקוח.

# החלטה 010: זהות והרשאות (Identity & Authorization)

**סטטוס:** הוכרע
**רלוונטי למימוש:** כן — מגדיר קוד שיש לכתוב

## הסוגיה

הסטרטר קובע את זהות המשתמש והרשאותיו כך:

```csharp
var userId = ParseUserId(Request.Headers["X-User-Id"].FirstOrDefault());
var isAdmin = string.Equals(
    Request.Headers["X-Is-Admin"].FirstOrDefault(), "true",
    StringComparison.OrdinalIgnoreCase);

private static int ParseUserId(string? value)
    => int.TryParse(value, out var userId) ? userId : 1;
```

זוהו שלוש בעיות:

| # | הבעיה | חומרה |
|---|---|---|
| 1 | **הלקוח מכריז על ההרשאה של עצמו.** כל בקשה עם `X-Is-Admin: true` מקבלת גישה מלאה. אין שום אכיפה בשרת | חמורה |
| 2 | **Fail-open.** `X-User-Id` חסר או פגום → המערכת מניחה בשקט משתמש 1 במקום לדחות את הבקשה | חמורה |
| 3 | **הזהות נקבעת בקונטרולר.** כל קונטרולר עתידי ישכפל את הלוגיקה, ומעבר לאותנטיקציה אמיתית ידרוש שינוי בכל אחד מהם | בינונית |

בעיה 1 מתנגשת ישירות עם דרישה מפורשת במסמך: *"ההרשאות נאכפות בשרת."* השרת אמנם מסנן, אך הוא מסנן לפי הרשאה שהתקבלה מהלקוח — כלומר האכיפה מדומה.

### הבחנה מרכזית

| מושג | השאלה שהוא עונה עליה | מצבו בסטרטר |
|---|---|---|
| **Authentication** (אימות) | *מי אתה?* | מדומה — `X-User-Id` הוא הצהרה לא מאומתת |
| **Authorization** (הרשאה) | *מה מותר לך?* | **לא נאכפת** — מגיעה מהלקוח |

הדרישות עוסקות ב**הרשאות**, לא באימות. במסמך מופיע: *"משתמש רגיל רואה רק בקשות שבבעלותו או מוקצות אליו; Admin רואה הכל."* אין דרישה ל-login, לניהול משתמשים או לניהול סיסמאות.

## החלופות שנשקלו

### א. להשאיר כפי שהוא ולתעד בלבד

- **בעד:** אפס עלות. ההערה `// For the exercise` בקוד מעידה שזהו פיגום מכוון של מחברי המבחן.
- **נגד:** דרישה מפורשת במסמך אינה מתקיימת. מועמד שאינו מזהה את הפער נראה כמי שלא קרא את הקוד.

### ב. אימות מלא (JWT + login)

מימוש `Users` עם סיסמאות, endpoint של התחברות, הנפקת JWT, `[Authorize]`, ו-interceptor ב-Angular.

- **בעד:** פותר את הבעיה במלואה.
- **נגד:**
  - אינו נדרש באף סעיף במסמך הדרישות
  - עלות מוערכת: יום עבודה מלא, על חשבון הדרישות שכן נבדקות (ביצועים, סינון, מיון, UI)
  - סותר את הנחיית המסמך: *"מעדיפים פתרון פשוט, ברור ומנומק על פני מורכב שלא נדרש"*
  - קוד אבטחה שנכתב בחיפזון הוא שטח חשוף בראיון ההמשך

### ג. תפקיד נקבע מהמסד; זהות נותרת מ-header ✅

הלקוח שולח `X-User-Id` בלבד. השרת טוען את המשתמש מטבלת `Users` וקורא משם את תפקידו. הכותרת `X-Is-Admin` **מוסרת לחלוטין**.

- **בעד:**
  - **ההרשאה נאכפת בשרת במלואה** — הלקוח אינו יכול להעניק לעצמו הרשאות
  - זהו המודל של מערכת אמיתית: הזהות מגיעה מבחוץ, התפקיד נקרא מהמסד
  - מוסיף ולידציה שלא הייתה: משתמש שאינו קיים נדחה ב-`401`
  - עלות: כשעה עד שעה וחצי
- **נגד:**
  - האימות עדיין מדומה — `X-User-Id` נותר הצהרה לא מאומתת
  - מוסיף Entity, `DbSet` ו-seed שאינם חלק מהפיצ'ר הנבדק

## ההחלטה

**חלופה ג׳, בגרסה מצומצמת.**

1. הכותרת `X-Is-Admin` **מוסרת**. התפקיד נקרא מטבלת `Users` לפי המזהה שהתקבל.
2. הזהות מחולצת מהקונטרולר ל-`ICurrentUser` — interface ב-`Application`, מימוש ב-`Api`/`Infrastructure`.
3. ברירת המחדל למשתמש 1 מוסרת. `X-User-Id` חסר, פגום, או מצביע על משתמש שאינו קיים → `401 Unauthorized`.
4. המימוש מבוסס-ה-headers **חסום מחוץ לסביבת Development** באמצעות כשל מפורש בעלייה.
5. **ללא** `IUserRepository` נפרד — המימוש פונה ל-`DbContext` ישירות מתוך שכבת ה-Infrastructure.

### נימוק הצמצום

`ICurrentUser` נקרא פעם אחת לכל בקשת HTTP, ותמיד לפי מפתח ראשי. Repository מלא (`GetAll`, `Search`, `Add`) יהיה תשתית שאיש אינו משתמש בה. הארכיטקטורה נשמרת ממילא: ה-interface ב-`Application`, המימוש ב-`Infrastructure`, ושכבת הלוגיקה אינה יודעת דבר על EF Core.

### 5. `Requests.Infrastructure/Identity/HeaderCurrentUser.cs`

```csharp
using Microsoft.AspNetCore.Http;
using Microsoft.EntityFrameworkCore;
using Requests.Application.Common;
using Requests.Domain.Entities;
using Requests.Infrastructure.Persistence;

namespace Requests.Infrastructure.Identity;

/// <summary>
/// מימוש לסביבת פיתוח בלבד.
/// הזהות מגיעה מכותרת X-User-Id; התפקיד נקרא מהמסד ולא מהלקוח.
/// </summary>
public sealed class HeaderCurrentUser : ICurrentUser
{
    private const string UserIdHeader = "X-User-Id";

    private readonly IHttpContextAccessor _accessor;
    private readonly RequestsDbContext _db;
    private CurrentUserInfo? _cached;

    public HeaderCurrentUser(IHttpContextAccessor accessor, RequestsDbContext db)
    {
        _accessor = accessor;
        _db = db;
    }

    public async Task<CurrentUserInfo> GetAsync(CancellationToken ct = default)
    {
        if (_cached is not null)
            return _cached;

        var header = _accessor.HttpContext?.Request.Headers[UserIdHeader].FirstOrDefault();

        if (!int.TryParse(header, out var userId))
            throw new UnauthenticatedException($"Header '{UserIdHeader}' is missing or invalid.");

        var user = await _db.Users
            .AsNoTracking()
            .FirstOrDefaultAsync(u => u.Id == userId, ct)
            ?? throw new UnauthenticatedException($"User '{userId}' does not exist.");

        _cached = new CurrentUserInfo(user.Id, user.Role == UserRole.Administrator);
        return _cached;
    }
}
```

> **caching בתוך הבקשה:** השירות נרשם כ-`Scoped`, כלומר instance אחד לכל בקשת HTTP. ה-caching מונע שאילתה חוזרת בכל גישה ל-`ICurrentUser` באותה בקשה.

### 11. עדכון CORS

```csharp
builder.Services.AddCors(options =>

        .WithOrigins("http://localhost:4200")
```

מעבר משתמש (לצורך הדגמה למראיין) מתבצע בבורר פשוט ב-UI שמשנה את המזהה בלבד. **הלקוח אינו שולח ואינו יודע דבר על תפקידים.**

## מה נותר מדומה

`X-User-Id` היא עדיין הצהרה לא מאומתת. ניתן לשלוח מזהה של משתמש אחר ולקבל את הרשאותיו. הדבר מטופל בשתי דרכים:

1. תיעוד מפורש ב-README
2. חסימה טכנית של המימוש מחוץ לסביבת פיתוח (סעיף 8)

## המעבר לפרודקשן

```csharp
public sealed class JwtCurrentUser : ICurrentUser
```

**מה לא נעשה:** `MatTableDataSource` על חיבוריו המובנים — `dataSource.sort = this.sort` ו-`dataSource.paginator = this.paginator`. החיבורים האלה מפעילים מיון ודפדוף **על המערך שנטען לזיכרון**, כלומר על 25 השורות של העמוד הנוכחי בלבד.

זו בדיוק התקלה ש-T13 מזהיר מפניה: מיון של 25 שורות מתוך אלפים מחזיר תשובה שגויה שנראית תקינה לחלוטין. בהתאם לדרישת *"יש להניח מיליוני רשומות"* ולהחלטה 004, המיון והדפדוף חייבים לרוץ במסד ולא בזיכרון.

**מה כן נעשה:**

| רכיב | תפקידו | הקלט שלו | הפלט שלו |

# החלטה 012: ניהול מצב החיפוש — RxJS מול Signals

**סטטוס:** הוכרע

## הסוגיה

מצב החיפוש כולל את ערכי הפילטר, שדה וכיוון המיון, מספר העמוד, התוצאות עצמן, ומצב הטעינה/שגיאה. השאלה היא באיזה מנגנון ריאקטיביות לנהל אותו.

**ההבחנה המהותית בין השניים:**

| | RxJS (Observables) | Signals |
|---|---|---|
| מה זה מייצג | רצף של ערכים לאורך זמן | מיכל שמחזיק ערך נוכחי |
| חוזק מרכזי | תיאום אסינכרוני: השהיה, ביטול, מיזוג | קריאה סינכרונית של "מה הערך עכשיו" |
| קריאת ערך נוכחי | דורש `BehaviorSubject` או אופרטור | ✅ ישיר |
| השהיה (debounce) | ✅ אופרטור מובנה | ❌ אין |
| ביטול בקשה קודמת | ✅ אופרטור מובנה | ❌ אין |

בקצרה: **סיגנלים מצוינים ל"מה הערך עכשיו"; RxJS מצוין ל"דברים שקורים לאורך זמן".** הפיצ'ר הזה מכיל את שניהם, והשאלה היא איזה מהם הליבה.

חשוב לציין ש-RxJS נמצא בצנרת בכל מקרה, ללא קשר להחלטה: `HttpClient` מחזיר Observable, `form.valueChanges` הוא Observable, ו-`ActivatedRoute.queryParams` (הנדרש לפי החלטה 013) הוא Observable.

## החלופות שנשקלו

### א. RxJS טהור ✅

הצינור כולו זרם אחד: שינוי בפילטר → השהיה → ביטול בקשה קודמת → קריאה לשרת → תוצאות. התבנית צורכת את התוצאות דרך ה-`async` pipe.

### ב. Signals טהור

כל המצב בסיגנלים, ו-`effect()` שמפעיל את הקריאה לשרת בעקבות שינוי.

**נפסל, משתי סיבות מהותיות:**

1. **אין השהיה ואין ביטול.** הדרישה ב-T12 היא `debounceTime(300)` ו-`switchMap`. בסיגנלים טהורים יש לממש ידנית `setTimeout` להשהיה, ומונה סידורי שמתעלם מתשובות מיושנות — כלומר כתיבה מחדש של `switchMap`, בקוד ארוך יותר ושביר יותר. ראה החלטה 014.
2. **`effect()` אינו מיועד לתזמור נתונים.** ההנחיה של Angular היא שאפקטים משמשים לתופעות לוואי (לוגים, DOM), ולא להפעלת קריאות רשת. מימוש שמפעיל HTTP מתוך `effect()` הוא דפוס שניתן לתקוף בקלות בביקורת קוד.

### ג. משולב — צינור RxJS, תצוגה בסיגנלים דרך `toSignal()`

הזרם מבצע את העבודה האסינכרונית, ו-`toSignal()` ממיר את התוצאה לסיגנל שהתבנית קוראת.

**היתרון:** הכלי הנכון לכל תפקיד. זהו הדפוס האידיאומטי בפרויקט Angular חדש היום.

**החיסרון:** שתי פרדיגמות ומושג גישור נוסף, ועוד API חדש יחסית (`@angular/core/rxjs-interop`) — בעמוד יחיד, תוספת בלי החזר מספק.

## ההחלטה

**RxJS טהור. התצוגה צורכת את התוצאות דרך ה-`async` pipe.**

## הנימוקים

1. **ליבת הפיצ'ר היא תיאום אסינכרוני.** הבעיה המרכזית כאן היא השהיית הקלדה וביטול בקשות מיושנות — בדיוק התחום שבו RxJS חזק, ובדיוק התחום שסיגנלים אינם מכסים.

2. **סיגנלים לא היו חוסכים כלום בליבה.** הם היו עוזרים רק בקצה התצוגה, ושם ה-`async` pipe נותן את אותה תוצאה בלי מושג נוסף.

3. **ניהול מנויים אוטומטי.** ה-`async` pipe נרשם לזרם ומבטל את המנוי עם השמדת הקומפוננטה — אין קוד ניקוי ידני ואין דליפת מנויים.

4. **פרדיגמה אחת.** מאחר ש-RxJS נוכח בצנרת בכל מקרה, הוספת סיגנלים הייתה מוסיפה שכבת גישור מבלי לפתור בעיה קיימת.

## מה סיגנלים כן היו משפרים

לשם הגינות: קריאת ערך נוכחי **מחוץ** לתבנית נוחה יותר בסיגנלים. ב-RxJS, "מה מספר העמוד כרגע" דורש `BehaviorSubject` או אופרטור, בעוד בסיגנל זו קריאה ישירה. בפיצ'ר הזה הצורך הזה מצומצם, ולכן זה לא הכריע — אבל זה יתרון אמיתי ולא ראוי להתעלם ממנו.

## מתי ההחלטה הייתה משתנה

- **מצב מקומי סינכרוני רב** — טפסים מורכבים, מצב UI נגזר, חישובים בין ערכים: שם `computed()` נותן ערך משמעותי ש-RxJS לא נותן בנוחות
- **מספר קומפוננטות שחולקות מצב נגזר** — סיגנלים היו מצמצמים קוד תיאום
- **בפרויקט חדש הנכתב מהיסוד היום**, הדפוס המשולב (חלופה ג׳) הוא ברירת המחדל האידיאומטית. הוא נדחה כאן משום שבעמוד יחיד מושג הגישור עולה יותר ממה שהוא חוסך — לא משום שהוא נחות

# החלטה 013: מיקום מצב הפילטר — הכתובת כמקור אמת יחיד

**סטטוס:** הוכרע
**רלוונטי למימוש:** כן — קובע את זרימת הנתונים בקומפוננטה

## הסוגיה

שני דברים צריכים לשקף את מצב החיפוש (פילטר, מיון, עמוד): המסך, ושורת הכתובת של הדפדפן. השאלה היא **מי מקור האמת** — כלומר מי מפעיל את מי.

זו אינה שאלה של סגנון. כל עוד שני מקומות מחזיקים את אותו מידע, קיים תרחיש שבו הם אינם מסכימים — וזהו בדיוק סוג הבאג שמתגלה בהדגמה חיה.

**הקשר להחלטה 002:** שם נבחר `GET` בין השאר בנימוק שתצוגה מסוננת צריכה להיות ניתנת לשיתוף ולשרוד רענון. ללא סנכרון לכתובת, הנימוק ההוא נשאר בלתי ממומש — וזו סתירה פנימית שקל לאתר.

## החלופות שנשקלו

### א. הקומפוננטה כמקור אמת, הכתובת כשיקוף

בטעינה נקראים ה-`queryParams` פעם אחת לאתחול. מכאן והלאה כל שינוי מעדכן את המצב הפנימי, מפעיל קריאה לשרת, ובנוסף נכתב לכתובת. איש אינו קורא את הכתובת בחזרה.

| בעד | נגד |
|---|---|
| מודל מחשבתי פשוט | כפתור "אחורה" אינו עובד — הכתובת משתנה ואיש אינו מאזין לה |
| אין סיכון ללולאת סנכרון | שני מקומות מחזיקים את אותו מידע, והסנכרון ביניהם מתוחזק ידנית |

### ב. הכתובת כמקור אמת ✅

הדבר היחיד שמפעיל קריאה לשרת הוא הזרם `ActivatedRoute.queryParams`. פעולות המשתמש אינן מביאות נתונים — הן **מנווטות**.

### ג. שירות עם `BehaviorSubject`

שכבה נוספת שמחזיקה את המצב ומסנכרנת לשני הכיוונים.

**נפסל.** מוצדק כשמספר קומפוננטות במספר מסלולים חולקות מצב. כאן יש עמוד אחד — זו תוספת מבנית בלי צורך, באותו נימוק שהוביל בהחלטה 001 לדחות CQRS.

## ההחלטה

**הכתובת (`queryParams`) היא מקור האמת היחיד.**

## המנגנון

**טעינה ראשונית או כניסה מקישור משותף:**

1. הזרם `queryParams` פולט את הערכים שבכתובת
2. הטופס מאותחל מהם — **בשקט** (ראה המלכודת למטה)
3. נשלחת קריאה לשרת
4. התוצאות מוצגות

**פעולת משתמש (סימון סטטוס, למשל):**

1. הטופס משתנה
2. נבנית כתובת חדשה, עם `page=1` (החלטה 015)
3. מתבצע ניווט — **וכאן זה נעצר**. לא נשלחת קריאה לשרת
4. הזרם `queryParams` פולט את הכתובת החדשה
5. נשלחת קריאה לשרת, והתוצאות מוצגות

**לחיצה על "אחורה":** הדפדפן מחזיר את הכתובת הקודמת → הזרם פולט → אותו מסלול בדיוק. אין קוד ייעודי.

## המלכודת: לולאת סנכרון

המנגנון מורכב משני חוקים שכל אחד מפעיל את השני:

1. הטופס משתנה → כותבים לכתובת
2. הכתובת משתנה → ממלאים את הטופס

ללא זהירות נוצר מעגל: המשתמש מסמן → נכתב לכתובת → הכתובת השתנתה → ממלאים את הטופס → **מילוי הטופס הוא בעצמו שינוי בטופס** → נכתב לכתובת שוב → וכן הלאה ללא סוף. הערך זהה בכל סיבוב, אך הקוד מגיב לעצם השינוי ולא לתוכנו.

**התיקון:** מילוי הטופס מתוך הכתובת מתבצע עם `{ emitEvent: false }` — כלומר "עדכן את הערך בלי לשדר אירוע שינוי". ההיגיון: שינוי שבוצע על ידי הקוד אינו פעולת משתמש, ורק פעולת משתמש אמורה לייצר כתובת חדשה.

> `distinctUntilChanged` אינו פתרון מספק כאן: כברירת מחדל הוא משווה לפי זהות אובייקט, ו-`valueChanges` מייצר אובייקט חדש בכל פליטה — כך שההשוואה תמיד תדווח "שונה". הוא שימושי כרשת ביטחון רק עם פונקציית השוואה לפי תוכן.

## החלטות נלוות

### `replaceUrl` בניווטים שמקורם בהקלדה

כל ניווט מייצר כניסה בהיסטוריית הדפדפן. אם כל מילת חיפוש מייצרת כניסה, "אחורה" יעבור אות-אות לאחור. לכן: ניווטים שמקורם בשדה הטקסט משתמשים ב-`replaceUrl: true`, ואילו שינויי מיון, עמוד וגודל עמוד מבצעים ניווט רגיל — שם "אחורה" הוא פעולה בעלת משמעות.

### ערכים מרובים ב-`queryParams`

`Router` של Angular מקבל מערך כערך פרמטר ומסדר אותו כפרמטר חוזר, בהתאמה לחוזה (החלטה 003):

```typescript
this.router.navigate([], {
  relativeTo: this.route,
  queryParams: { status: ['New', 'InProgress'], page: 1 },
  replaceUrl: fromTextInput
});
// ‎→ ?status=New&status=InProgress&page=1
```

> אין שימוש ב-`queryParamsHandling: 'merge'`. אובייקט הפרמטרים נבנה שלם בכל ניווט, כך
> שפרמטר שהוסר מהפילטר אכן נעלם מהכתובת. מיזוג היה משאיר שאריות של סינון קודם.

בבניית ה-`HttpParams` לקריאה עצמה נעשה שימוש ב-`append` ולא ב-`set`, כפי שמתועד בהחלטה 003.

## מתי ההחלטה הייתה משתנה

- **מצב שאינו אמור להופיע בכתובת** — למשל טיוטה שהמשתמש עורך ועדיין לא החיל: שם הכתובת אינה המקום הנכון
- **פילטר עשיר במיוחד** שהיה הופך את הכתובת לארוכה מדי — ראה גבולות האורך שנדונו בהחלטה 002
- **אם הלולאה הייתה מתגלה כיקרה לייצוב** — חלופה א׳ הייתה נפילה לגיטימית שעדיין עומדת בדרישת T15 כפי שנוסחה (העתקה לטאב חדש ושחזור), במחיר ויתור על "אחורה"

# החלטה 014: הקלדה מהירה — השהיה ומניעת Race Conditions

**סטטוס:** הוכרע

## הסוגיה

הקלדה בשדה החיפוש מייצרת שתי בעיות **נפרדות**, שקל להתבלבל ולחשוב שהן אחת. ההשהיה פותרת רק את הראשונה.

---

## בעיה א: נפח קריאות מיותר

הקלדת `REQ-01` היא שש הקשות. ללא הגנה נשלחות שש קריאות לשרת, כשחמש מהן חסרות משמעות — איש אינו מתעניין בתוצאות עבור `R` או `RE`. תחת ההנחה של מיליוני רשומות, כל קריאה כזו היא עבודה אמיתית במסד.

**הפתרון: `debounceTime(300)`** — הקריאה נשלחת רק לאחר שהמשתמש חדל להקליד למשך 300 מילישניות. כל הקשה מאפסת את הספירה.

**נימוק המספר:** מקליד מהיר משאיר 100–200 מילישניות בין הקשות, ולכן 300 מסמן עצירה אמיתית. ב-100 עדיין נשלחות קריאות בתוך ההקלדה; ב-1000 נוצרת השהיה מורגשת שנתפסת כתקלה.

**בנוסף `distinctUntilChanged()`** — ערך זהה לקודם אינו נשלח כלל. תופס מקרים כמו מחיקה והחזרה של אותה אות, או לחיצה על מקש שמייצר אירוע בלי לשנות טקסט.

---

## בעיה ב: תשובות החוזרות בסדר הפוך

**זו הבעיה שההשהיה אינה פותרת.** ההשהיה מפחיתה את מספר הקריאות; היא אינה מבטיחה דבר לגבי סדר החזרה.

**התרחיש:**

1. המשתמש מקליד `REQ-1`, עוצר — נשלחת קריאה א׳
2. ממשיך ל-`REQ-12`, עוצר — נשלחת קריאה ב׳
3. השרת עמוס; קריאה א׳ נמשכת 800ms, קריאה ב׳ נמשכת 200ms
4. תשובה ב׳ חוזרת ראשונה — מוצגות התוצאות של `REQ-12` ✅
5. תשובה א׳ חוזרת אחריה — מוצגות התוצאות של `REQ-1` ❌

**התוצאה:** בשדה החיפוש כתוב `REQ-12`, ובטבלה מוצגות התוצאות של `REQ-1`. אין שגיאה ואין אינדיקציה — פשוט תשובה שגויה על המסך.

**העיקרון:** אין שום הבטחה שתשובות יחזרו בסדר שבו הבקשות נשלחו.

### החלופות לטיפול

| אופרטור | התנהגות | מתאים כאן? |
|---|---|---|
| **`switchMap`** ✅ | קריאה חדשה **מבטלת** את הקודמת. התשובה הישנה לא תגיע כלל | ✅ הבחירה הנכונה לחיפוש |
| `mergeMap` | כל הקריאות רצות במקביל וכל התשובות מטופלות | ❌ זהו הבאג שתואר למעלה |
| `concatMap` | תור — כל קריאה ממתינה לסיום קודמתה | ❌ המשתמש ממתין לכל התור ורואה תוצאות ישנות מהבהבות. מתאים לשמירות עוקבות |
| `exhaustMap` | מתעלם מבקשות חדשות כל עוד אחת באוויר | ❌ הקלט האחרון של המשתמש נזרק. מתאים למניעת לחיצה כפולה על "שלח" |
| מונה סידורי ידני | תיוג כל קריאה והתעלמות מתשובות שאינן העדכניות | עובד, אך זו עבודה ידנית ש-`switchMap` נותן באופרטור אחד |

## ההחלטה

**`debounceTime(300)` + `distinctUntilChanged()` על שדה הטקסט בלבד; `switchMap` על כל הקריאות.**

## על מה חלה ההשהיה — ועל מה לא

זו החלטת התכנון המהותית כאן.

| מקור השינוי | השהיה? | נימוק |
|---|---|---|
| שדה הטקסט | ✅ 300ms | מייצר עשרות אירועים בשנייה |
| תיבות סטטוס, סוג, תאריכים | ❌ מיידי | פעולה בודדת ומכוונת |
| לחיצת מיון | ❌ מיידי | המשתמש מצפה לתגובה מיידית |
| מעבר עמוד, שינוי גודל עמוד | ❌ מיידי | כנ"ל |
| מחליף המשתמשים | ❌ מיידי | כנ"ל |

השהיה של פעולות בדידות מוסיפה עיכוב מורגש ללא כל תועלת. **ההגנה מפני סדר הפוך (`switchMap`), לעומת זאת, חלה על כולן** — גם שתי לחיצות מיון עוקבות עלולות לחזור בסדר הפוך.

## מבנה הצינור

בשילוב עם החלטה 013, המסלול הוא:

```
שדה טקסט → debounce(300) → distinctUntilChanged ─┐
                                                  ├→ ניווט (שינוי הכתובת)
שאר הפקדים ──────────────── מיידי ───────────────┘
                                                        ↓
                        queryParams → switchMap → HttpClient → תוצאות
```

שתי תכונות נובעות מהמבנה הזה: ההשהיה יושבת **לפני** הניווט, ולכן היסטוריית הדפדפן אינה מתמלאת בכתובת לכל אות; וה-`switchMap` יושב על המעבר היחיד מכתובת לשרת, ולכן הוא מגן על כל סוגי השינויים בנקודה אחת.

## נקודת מימוש: חיווי הטעינה

אם חיווי הטעינה מודלק רק כשהקריאה נשלחת בפועל, במהלך 300 המילישניות של ההשהיה המסך נראה קפוא. החיווי מודלק כבר בעת ההקלדה, ולא רק בעת שליחת הקריאה. פרט קטן, אך הוא ההבדל בין ממשק שנתפס כמהיר לאחד שנתפס כתקוע. קשור ל-T14.

## מתי ההחלטה הייתה משתנה

- **חיפוש יקר במיוחד בצד השרת** — הייתי מעלה את ההשהיה, או עוברת לחיפוש בלחיצה מפורשת במקום בהקלדה
- **דרישה להצגת תוצאות חלקיות מצטברות** — `switchMap` היה שגוי, שכן הוא מבטל תוצאות ביניים
- **שרת שאינו תומך בביטול בקשות** — הביטול היה חוסך רק עבודה בקליינט ולא בשרת, אך עדיין נדרש לנכונות

# החלטה 015: Allow-List המיון בקליינט, ואיפוס העמוד

**סטטוס:** הוכרע

## הסוגיה

שני עניינים נפרדים הנוגעים למיון בצד הלקוח:

1. היכן יושבת רשימת השדות הניתנים למיון, וכיצד היא נאכפת
2. מה קורה כאשר המשתמש משנה מיון בעודו בעמוד 7

---

## חלק א: ה-Allow-List

### רקע — מדוע הרשימה קיימת בשרת

השרת מקבל את `sortBy` וצריך להפוך אותו להוראת מיון במסד. העברה ישירה של קלט הלקוח לתוך `OrderBy` דינמי הייתה מאפשרת למיין לפי כל שם שדה שהלקוח ימציא. לכן השרת מחזיק רשימה סגורה של ארבעה שדות — `requestNumber`, `status`, `requestType`, `createdAt` — וכל ערך מחוץ לה מוחזר כ-`400`.

הרשימה משרתת שתי מטרות בו-זמנית: **גבול אבטחה** (אין `OrderBy` דינמי מקלט משתמש) ו**חוזה ביצועים** (רק שדות שהתחייבנו לשרת ביעילות).

### הבחנה מרכזית: הקליינט אינו אוכף

**האכיפה נמצאת בשרת בלבד.** הדפדפן אינו יכול לעצור איש — כל אחד יכול לערוך את הכתובת, לפתוח כלי מפתחים, או לשלוח בקשה ללא דפדפן כלל.

> הדימוי: על הדלת יש שלט "לעובדים בלבד", ובדלת יש מנעול. השלט אינו נועל דבר — הוא חוסך מאנשים ללכת לדלת שלא תיפתח. **הרשימה בקליינט היא השלט; הבדיקה בשרת היא המנעול.**

לכן העותק בקליינט משרת שתי מטרות צנועות בלבד: לקבוע אילו כותרות עמודה יהיו לחיצות, ולמנוע שליחת קריאה שידוע מראש שתיכשל.

### המימוש: קבוע יחיד, שני שימושים

רשימה אחת של ארבעת השדות המותרים, המשמשת ל:

1. **בניית הטבלה** — רק עמודה שברשימה מקבלת את הדירקטיבה `mat-sort-header`. עמודת בעלים/מוקצה אינה מקבלת אותה, ולכן אינה לחיצה. הנגישות (`aria-sort`, ניווט מקלדת) מגיעה מהדירקטיבה עצמה — ראה החלטה 011.
2. **אימות הערך המגיע מהכתובת** — נדרש בעקבות החלטה 013: מרגע שהכתובת היא מקור האמת, כל ערך עשוי להגיע ממנה, כולל מקישור ששותף.

### ההחלטה: `sortBy` לא חוקי → נפילה שקטה לברירת המחדל

ערך שאינו ברשימה (`?sortBy=ownerName`) מוחלף ב-`createdAt`, וכך קישור פגום עדיין נפתח לעמוד עובד במקום למסך שגיאה.

**היחס לעיקרון שנקבע בהחלטה 003.** שם נקבע במפורש: *"התעלמות שקטה מערך לא מוכר היא באג — הלקוח יקבל תוצאות שלא ביקש ולא יידע על כך."* אין כאן סתירה, וההבחנה מהותית:

| | סינון | מיון |
|---|---|---|
| מה נקבע | **אילו** שורות מוחזרות | **באיזה סדר** בלבד |
| נזק בהתעלמות שקטה | המשתמש מסתכל על נתונים שלא ביקש ואינו יודע זאת | המשתמש מקבל את השורות הנכונות, בסדר אחר |
| ההחלטה | `400` מפורש (החלטה 003) | נפילה שקטה לברירת מחדל |

ערכי **סינון** לא חוקיים המגיעים מהכתובת אינם מסוננים בקליינט — הם נשלחים לשרת ומוחזרת שגיאת `400` עם `ProblemDetails`, בדיוק כפי שהחוזה מתאר.

## חלק ב: איפוס העמוד

### מה משמעותו של "עמוד 7"

מספר עמוד אינו ישות עצמאית. הוא הוראה: *"דלג על 150 השורות הראשונות, והחזר את 25 הבאות"*. ההוראה אינה אומרת דבר על **אילו** שורות — היא מציינת מיקום בתוך סדר מסוים. משנים את הסדר, והמיקום מאבד את משמעותו.

### מצב כשל 1 — שינוי מיון: שורות שרירותיות

המשתמש בעמוד 7 של רשימה ממוינת לפי תאריך, ולוחץ על "סטטוס". אם העמוד נותר 7, ההוראה "דלג על 150" חלה כעת על רשימה שסודרה אחרת לגמרי. השורות שהוצגו לפני רגע נעלמו, והוחלפו בשורות מאמצע רשימה חדשה, ללא קשר נראה לעין.

> כמו להחזיק אצבע על עמוד 150 בספר, ואז שמישהו מחליף את הספר. העמוד קיים — הוא פשוט אינו קשור למה שנקרא.

ומה המשתמש התכוון בלחיצה על "סטטוס"? לראות מי בא ראשון לפי סטטוס. כלומר עמוד 1.

### מצב כשל 2 — שינוי סינון: מסך ריק מטעה

חמור יותר, ושייך לשינויי סינון. המשתמש בעמוד 7; הסינון החדש מחזיר 40 תוצאות בלבד, כלומר שני עמודים. עמוד 7 אינו קיים.

השרת יחזיר `items: []` עם `totalCount: 40` — התנהגות נכונה לפי החוזה. אך המשתמש יראה "אין תוצאות מתאימות", בעוד שקיימות 40 תוצאות והוא פשוט עומד מעבר לקצה הרשימה. האפליקציה מסרה מידע שגוי ללא כל שגיאה.

### ההחלטה

**כל שינוי שאיננו מעבר עמוד מאפס את העמוד ל-1.**

| שינוי | מאפס? | הערה |
|---|---|---|
| ערך פילטר כלשהו | ✅ | מונע את מצב כשל 2 |
| שדה מיון | ✅ | מונע את מצב כשל 1 |
| **כיוון מיון בלבד** | ✅ | קל לשכוח. היפוך הכיוון משנה את הסדר לחלוטין |
| **גודל עמוד** | ✅ | עמוד 7 ב-25 הוא שורות 151–175; ב-100 הוא 601–700 |
| **מחליף המשתמשים** | ✅ | קל לשכוח. משנה את קבוצת התוצאות דרך מסנן ההרשאות, ועלול לייצר את מצב כשל 2 |
| מעבר עמוד | ❌ | זו הפעולה עצמה |

### חלופה שנשקלה ונדחתה — שימור מיקום בשינוי גודל עמוד

ניתן לחשב לאיזה עמוד חדש שייכת השורה הראשונה שהוצגה, ולעבור אליו — כך שהמשתמש נשאר באותו מקום ברשימה.

**נדחתה:** לוגיקה נוספת שיש לכתוב ולהסביר, עבור שיפור חוויה שולי. איפוס לעמוד 1 הוא התנהגות צפויה ומקובלת.

### המימוש

זהו אינו מנגנון נפרד. בהתאם להחלטה 013 קיים מקום יחיד הבונה את פרמטרי הכתובת החדשים, ובתוכו הכלל הוא שורה אחת: כל שינוי שאיננו דפדוף מציב `page=1`. אין מצב נוסף לתחזק ואין סנכרון בין שני מקומות.

> חץ המיון המוצג בכותרת נגזר אף הוא מהכתובת: `[matSortActive]` ו-`[matSortDirection]` נקשרים מהערכים שב-`queryParams` ולא ממצב פנימי של הרכיב. זהו יישום ישיר של כלל המימוש בהחלטה 011 — הרכיב מציג ומנפיק, ואינו מחזיק מצב.

## מתי ההחלטה הייתה משתנה

- **טבלה שבה שורה נבחרת היא ההקשר** (למשל עריכה מרובת-שלבים) — שם קפיצה לעמוד 1 הייתה מאבדת את מקומו של המשתמש, והיה מקום לשמר מיקום או לסמן את השורה
- **מיון בצד הלקוח** — אילו כל התוצאות היו בזיכרון, שינוי מיון לא היה מצריך קריאה ואיפוס העמוד היה נשקל אחרת. נשלל בהחלטה 004
- **אילו ה-allow-list היה גדל משמעותית** — הייתי שוקלת לייצר אותו מתוך הגדרת העמודות במקום להחזיק רשימה נפרדת, כדי למנוע סטייה בין השתיים
